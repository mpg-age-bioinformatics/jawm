**JAWM: GLP/GCP readiness and resilience to change — 8 September 2026**

**Conclusion: useful engineering foundations; insufficient evidence of a validated, compliant deployment.** JAWM could become a component of a GLP/GCP system. That would require both software changes and an operational validation package owned by the deploying organisation. The current repository does not support treating JAWM as already GLP/GCP compliant, or assuming that its existing tests will reliably preserve a validated state after changes.

The strongest evidence is executable software for orchestration, logging, versioned module resolution and regression checking. The weakest areas are enforceable integrity checks, preservation of complete records, and documented validation/change governance. Several weaknesses are observed behaviors, rather than simply missing documentation.

This review covers commit `9e519079af55d5124e26f59445bd1985e9c7417e` (30 July 2026). The working tree was clean when reviewed. Scope: GLP, GCP and general future regulated use, as requested. With no jurisdiction specified, OECD GLP and EU/ICH GCP are the principal reference points; FDA Part 11 is conditional on the applicable records and US regulatory scope. This is a repository readiness assessment, not a facility inspection or formal validation approval. No application code was changed.

**What was examined and how much it supports**

The review inventoried the tracked source, documentation, packaging and eight GitHub workflow files, and traced critical execution, resume, hashing, retry, configuration and module-loading paths. It examined `test/base_test.py` (57 numbered cases), `test/git_test.py`, and the `jawm-test` runner. Six groups of targeted synthetic probes were executed against the checkout using Python 3.11.6 on macOS. The full existing suite, live Git integration, Slurm, Kubernetes, Docker and Apptainer execution were not run. Historical CI results, repository protection settings, deployed infrastructure and organisational quality records were not inspected.

**Other material gaps established by code/document inspection**

Version pinning is available but not enforced. A locally exported workflow's `.commit` is a text stamp, and modification checking uses file modification times. A real Git checkout is checked for dirty state, but only a warning is emitted. Neither path establishes that only approved, unchanged code can execute. Source and runtime details are logged, but the package version remains `0.1.0`; dependencies have lower bounds rather than a locked deployed environment, and the documented `pip freeze` step is manual. A library does not need to lock every downstream user's environment, but each validated deployment needs its own exact baseline. [Source checks](/Users/jboucas/jawm/jawm/cli.py:2701), [package](/Users/jboucas/jawm/pyproject.toml:6), [manual environment snapshot](/Users/jboucas/jawm/docs/examples/reproducibility.md:301).

Container use helps constrain execution, but tags can change, and code does not require an immutable image digest. Kubernetes can infer an image from the script shebang. Requesting a container environment without providing a container can fall back to local execution. This flexibility needs a restricted, qualified configuration for regulated work. No automatic complete dependency/data/environment attestation was identified. [Fallback](/Users/jboucas/jawm/jawm/process.py:475), [Kubernetes inference](/Users/jboucas/jawm/jawm/_process_kubernetes.py:223).

The automatic “input history” normally hashes a set of six-character process prefixes. It is not a content inventory of all scientific inputs; hashing these shortened identifiers again cannot recover omitted information. Prefixes also have only 24 bits of distinguishing information, and resume searches for a prefix substring in a folder name. Declaring `inputs` and `outputs` does not automatically activate content verification in the inspected code. [Automatic hash](/Users/jboucas/jawm/jawm/cli.py:992), [input/output assignment](/Users/jboucas/jawm/jawm/process.py:448).

CLI transcript names use module name and a timestamp with second resolution, then open with `mode="w"`. Concurrent starts for the same label and log directory within one second can therefore target the same file. This is a static collision finding; concurrency was not reproduced. Hash histories are append operations on ordinary writable files, and manifests follow the mutable baseline's overwrite policy; they are not independently protected, complete per-run archives. No authenticated actor/reason/approval event model or tamper-protected retention mechanism was found. [Transcript naming](/Users/jboucas/jawm/jawm/cli.py:2210), [history append](/Users/jboucas/jawm/jawm/cli.py:957).

`jawm-monitor clean` removes monitoring records and optionally Git caches, with confirmation and dry-run options; it should not be described as automatically deleting all workflow output. Nevertheless, no regulated retention/hold/authorised-disposal layer was identified. The reproducibility example explicitly removes original reports and says they are not recoverable from logs. Regenerating a result is not restoring or retaining its original record. External backups could address part of this, but no backup inventory, restore-test result or continuity exercise was supplied. [Cleanup](/Users/jboucas/jawm/jawm/cli_monitor.py:939), [example](/Users/jboucas/jawm/docs/examples/reproducibility.md:164).

CI is useful but does not yet evidence controlled qualification. Local core tests are configured for push/PR on Python 3.8, 3.10 and 3.13. Separate Slurm and Kubernetes workflows are manually triggered and randomly sample versions; they do not demonstrate qualification of an explicitly approved deployment matrix on every release. No explicit validation artifact upload/retention step was found. Core tests clean generated evidence and can skip unavailable backends. Some tests correctly confirm the current informational-mismatch behavior, including exit 0, so passing them would not by itself establish the stricter acceptance behavior proposed here. [Local CI](/Users/jboucas/jawm/.github/workflows/smoke_test.yaml:3), [Slurm matrix](/Users/jboucas/jawm/.github/workflows/smoke_slurm.yaml:4), [Kubernetes matrix](/Users/jboucas/jawm/.github/workflows/smoke_k8s.yaml:4), [existing mismatch assertion](/Users/jboucas/jawm/test/base_test.py:4479).

The public documentation says “GxP-ready by design”, while `gxp.md`, `testing.md`, `development.md` and `version-log.md` remain placeholders. Detailed module-testing documentation does exist, so it would be inaccurate to say testing is wholly undocumented. Still, the broad readiness claim is stronger than the evidence reviewed. A supportable interim wording would be: “Provides provenance and reproducibility features that can support validation within a controlled GLP/GCP deployment.” [Claim](/Users/jboucas/jawm/docs/index.md:26), [GxP page](/Users/jboucas/jawm/docs/gxp.md:1).

**Regulatory interpretation and scope**

For GLP, OECD No. 17 uses lifecycle validation and risk assessment, and addresses requirements, testing, change/configuration management, audit trails, security, archiving and recovery. Its operational change provisions explicitly connect retesting to preserving validation status. The linked document is the 2016 guidance reissued in 2022 with a footnote addition. These expectations apply to the computerised system in its operating context, not simply a software package. [OECD No. 17](https://www.oecd.org/content/dam/oecd/en/publications/reports/2016/04/application-of-glp-principles-to-computerised-systems_7d05366e/e3c9cda5-en.pdf).

GLP data-integrity assessment also depends on understanding the entire data flow and the criticality of its records. For JAWM this means identifying which raw data, intermediate results, scripts, metadata and final outputs are necessary for study reconstruction; an output hash alone cannot settle that question. [OECD No. 22](https://www.oecd.org/en/publications/glp-data-integrity_45779212-en.html).

For GCP, ICH E6(R3) Annex 1 sections 4.2–4.3 address data governance and computerised systems, including risk-based validation before use and following changes, record retention, security and responsibilities. For a scientific workflow, both the execution platform and the trial-specific analysis/configuration need an appropriate evidence basis; orchestrator tests do not validate scientific conclusions. [ICH E6(R3), Principles and Annex 1](https://www.ema.europa.eu/en/documents/scientific-guideline/ich-e6-r3-guideline-good-clinical-practice-gcp-step-5_en.pdf).

The EMA computerised-systems guideline supplies more detailed expectations for test evidence, controlled release, periodic review and change control. Annex 2 sections A2.6–A2.10 provide a direct benchmark for the missing release/change evidence. Annex 3 covers user management. [EMA computerised systems and electronic data guideline](https://www.ema.europa.eu/en/documents/regulatory-procedural-guideline/guideline-computerised-systems-and-electronic-data-clinical-trials_en.pdf).

For future regulatory changes, the EU E6(R3) Principles and Annex 1 have applied since 23 July 2025. Annex 2 was adopted in June 2026 and is listed to take effect on 15 January 2027. Its relevance depends on trial design; it is not a universal software feature checklist. Maintain a regulatory applicability review rather than treating future guidance as already effective. [EMA current and upcoming E6 versions](https://www.ema.europa.eu/en/ich-e6-good-clinical-practice-scientific-guideline).

FDA Part 11 applicability must be assessed against the electronic records and underlying FDA requirements involved. An electronic-signature subsystem is not automatically required inside this workflow engine merely because it may support regulated work; any required approvals/signatures can be handled by a suitably controlled linked system. EU GMP Annex 11 is not the principal GLP/GCP benchmark for this request. [FDA Part 11 scope guidance](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/part-11-electronic-records-electronic-signatures-scope-and-application).

**Practical route to a defensible deployment**

The following is an engineering and validation proposal based on the observed gaps, not a claim that any particular product architecture is mandated.

1. **Define and restrict the first intended use.** Select one named GLP study phase or GCP analysis workflow, one backend and a controlled environment. Specify raw/source records, approved scientific method, required outputs, users, interfaces and review responsibilities. Assess risks to study validity, trial results and participant protection as applicable. Decide what JAWM owns and what the surrounding platform owns.
2. **Repair or demonstrably contain the high-priority failure modes.** Correct current-run hash comparison, failure precedence, dataset hashing, resume verification and retry record retention. Add targeted negative tests with explicit expected outcomes. Include missing outputs, unreadable evidence, interrupted jobs, skipped prerequisites, tampered baselines and simultaneous runs. Freeze affected capabilities until the proposed restrictions have been qualified.
3. **Create a complete run evidence bundle.** Use a unique run ID and separate attempt IDs. Capture the full JAWM/workflow revisions and actual source identity, selected workflow, effective configuration, relevant non-secret environment settings, immutable container identity, scientific reference-data versions, input/output manifest, dependency graph, all attempt outcomes, operator attribution and review linkage. Preserve original records in an access-controlled archive with integrity checks. Avoid copying credentials into provenance.
4. **Validate a fixed deployment.** Establish approved requirements and risks, trace them to platform and scientific-workflow tests, execute on the actual deployment, retain results and deviations, and approve release. Preserve the environment/artifacts needed to reconstruct it. Produce evidence that access controls, archive retrieval and recovery work. Reuse assessed supplier/developer evidence where appropriate; do not assume it replaces deployment-specific checks.
5. **Maintain the state through controlled changes.** Require a documented impact assessment, affected requirements, justified test selection, reviewed results/deviations and authorised promotion for each proposed production change. Keep development and production baselines separate. Preserve previous validation packages and study records, including when the analysis changes intentionally.

| Change | Proposed impact assessment and evidence |
|---|---|
| JAWM code or configuration precedence | Review affected execution semantics; test success/failure, dependencies, skip/resume, retries, status propagation and provenance on the approved backend. |
| Workflow logic, algorithm or scientific tool | Reassess scientific validity with independently justified expected results, representative datasets, boundary cases and predefined tolerances. Explain intended changes before approving a new baseline hash. |
| Input/reference data or annotation database | Identify the new dataset/version, verify transfer/content integrity, assess scientific consequences and invalidate affected reusable results. |
| Python packages or container image | Capture exact old/new identities, inspect relevant changes, test affected functions and end-to-end outputs; retain the approved artifacts. |
| Scheduler, operating system, storage or hardware | Reassess execution, resource limits, permissions, transfers, interruption recovery and result/evidence preservation in the changed environment. |
| Record format, migration or archive platform | Verify preservation of data and metadata, old-record readability, export and restore; retain migration evidence and prior readers where needed. |
| Protocol, regulatory guidance or intended use | Update applicability and risk assessments, requirements, training and validation scope before applying affected functionality. |

Do not interpret “same hash” as proof of scientific correctness. An erroneous workflow can reproduce the same erroneous result. Conversely, justified software or scientific changes may legitimately produce different bytes. Acceptance needs predetermined scientific criteria and review, with hashes used for identity/integrity where appropriate.

**Responsibilities and evidence still needed outside the repository**

The library can remain a relatively small workflow engine. OS/scheduler identity, managed execution, permissions, protected archives and an external quality/document system can supply many surrounding controls. Such controls need explicit allocation and demonstrated effectiveness; users able to replace scripts, results and their reference hashes would defeat a nominally protected workflow. An archive must capture records before in-place retries destroy them. GLP facility responsibility for IT security remains even when services are outsourced. [OECD No. 25, GLP and IT Security](https://www.oecd.org/en/publications/oecd-position-paper-on-good-laboratory-practice-and-it-security_910b7bd2-en.html).

Before changing this assessment to “supported for the specified regulated use”, obtain the intended-use/requirements and risk documents; named facility/study or sponsor/system/QA owners; approved validation results and deviations; actual CI/release evidence and production baseline; user/access/training records; backup, archive and restore-test records; and controlled change examples. For GCP, also establish any required confidentiality, blinding and trial-specific access boundaries. These items may exist elsewhere; their absence from this checkout is not proof of organisational absence.

The most convincing next milestone is **one controlled workflow and deployment, with the reproduced integrity defects resolved, an approved validation package, and a successfully documented upgrade plus archive/restore exercise**. That would provide concrete evidence that JAWM can support GLP/GCP work and remain fit for its intended use as it changes.
