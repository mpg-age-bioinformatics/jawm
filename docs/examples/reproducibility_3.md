# Reproducing a Remote FastQC Workflow

This example runs `jawm_fastqc` without manually cloning its repository.

The workflow is identified by an exact Git commit:

```text
jawm_fastqc@<commit>
```

The example:

1. Downloads a FASTQ file into `raw_data/`.
2. Defines the FastQC variables and output hash in one YAML file.
3. Runs the pinned remote workflow.
4. Deletes the first generated output.
5. Repeats the same JAWM command.
6. Validates the second output against the hash stored by the first run.

The final layout is:

```text
fastqc-remote-reproducibility/
├── raw_data/
│   └── my_test_file_1.fastq.gz
├── fastqc.yaml
├── fastqc_output/
└── logs/
```

## 1. Create the Working Directory

```bash
mkdir fastqc-remote-reproducibility
cd fastqc-remote-reproducibility
mkdir raw_data
```

## 2. Download the FASTQ Input

Download the test data:

```bash
curl -L \
  -o ./raw_data/my_test_file_1.fastq.gz \
  https://ndownloader.figshare.com/files/57999445
```

The expected MD5 checksum is:

```text
13fb536154e7cf36a394d9b09ff99b7a
```

On Linux, verify it with:

```bash
printf '%s  %s\n' \
  '13fb536154e7cf36a394d9b09ff99b7a' \
  './raw_data/my_test_file_1.fastq.gz' \
  | md5sum --check -
```

On macOS, verify it with:

```bash
test \
  "$(md5 -q ./raw_data/my_test_file_1.fastq.gz)" = \
  "13fb536154e7cf36a394d9b09ff99b7a"
```

The command exits successfully when the downloaded file has the expected content.

## 3. Create the FastQC YAML File

Create `fastqc.yaml`:

```yaml
- scope: process
  name: fastqc
  parallel: false
  var:
    mk.fastqc_output: "./fastqc_output"
    map.f: "./raw_data/my_test_file_1.fastq.gz"

- scope: hash
  include: ./fastqc_output/my_test_file_1_fastqc/fastqc_data.txt
  overwrite: false
```

The process variables tell FastQC where to find its input and where to write its output:

```yaml
mk.fastqc_output: "./fastqc_output"
map.f: "./raw_data/my_test_file_1.fastq.gz"
```

The hash section selects the extracted FastQC result:

```yaml
include: ./fastqc_output/my_test_file_1_fastqc/fastqc_data.txt
```

On the first run, the hash file does not exist yet. JAWM creates it from the generated `fastqc_data.txt` and then validates the reference.

On the second run, `overwrite: false` preserves the hash from the first run. JAWM compares the new result with that existing hash.

## 4. Run the Workflow for the First Time

Using a commit - eg. 6c73866090e035efa2ac39b88e3b67a22e463ffb - keeps the workflow source fixed. JAWM retrieves the remote module automatically, so the user does not need to run `git clone`.

JAWM may create a local resolved-module directory as part of its normal remote-module handling. That directory is managed by JAWM; it is not a manually prepared workflow checkout.

Run a pinned `test` workflow:

```bash
jawm jawm_fastqc@6c73866090e035efa2ac39b88e3b67a22e463ffb test \
  -p ./fastqc.yaml \
  -l ./logs
```

FastQC writes its output under:

```text
fastqc_output/
├── my_test_file_1_fastqc.html
├── my_test_file_1_fastqc.zip
└── my_test_file_1_fastqc/
    └── fastqc_data.txt
```

JAWM writes the reference hash under:

```text
logs/jawm_hashes/fastqc.hash
```

Display it:

```bash
cat ./logs/jawm_hashes/fastqc.hash
```

The first transcript reports a new hash:

```text
[hash] STATUS: NEW
[hash] Generated user-defined hash matched reference
```

## 5. Delete the First Output

Delete the first generated output:

```bash
rm -rf ./fastqc_output
```

This ensures that the second workflow runs FastQC again instead of skipping it because output already exists.

The generated reports from the first run are removed and are not recoverable from the log directory. They can be regenerated by running the workflow again.

Do not move or delete `logs/`. Its `fastqc.hash` is the reference for the second run.

The layout before the second run is:

```text
fastqc-remote-reproducibility/
├── raw_data/
├── fastqc.yaml
└── logs/
```

## 6. Run the Same Workflow Again

Repeat the exact same JAWM call:

```bash
jawm jawm_fastqc@6c73866090e035efa2ac39b88e3b67a22e463ffb test \
  -p ./fastqc.yaml \
  -l ./logs
```

The second run:

1. Uses the same pinned workflow commit.
2. Reads the same FASTQ path.
3. Creates a new `fastqc_output/`.
4. Calculates a new hash from `fastqc_data.txt`.
5. Compares it with `logs/jawm_hashes/fastqc.hash`.

Because `overwrite: false`, the second run cannot replace the reference hash.

## 7. Check Whether Run 2 Reproduced Run 1

If the output from the second run matches the hash created by the first run, JAWM prints:

```text
[hash] STATUS: MATCHED
[hash] Generated user-defined hash matched reference
```

The command completes successfully.

If the output is different, JAWM prints:

```text
[hash] STATUS: MISMATCHED
[hash] Generated user-defined hash does NOT match reference
```

and exits with code `73`.

Display the hash messages from both runs:

```bash
grep '\[hash\]' ./logs/jawm_runs/fastqc_*.log
```

Display the reference hash:

```bash
cat ./logs/jawm_hashes/fastqc.hash
```

Display the hash history:

```bash
cat ./logs/jawm_hashes/fastqc_user_defined.history
```

The history contains an entry for each run. When reproduction succeeds, both entries contain the same SHA-256 value.

## 8. Check Both Process Exit Codes

List the FastQC exit-code files in ascending path order:

```bash
find ./logs -name fastqc.exitcode -print \
  | sort \
  | while IFS= read -r exitcode_file; do
  printf "%s: " "$exitcode_file"
  cat "$exitcode_file"
  printf "\n"
done
```

Each successful FastQC process should have exit code `0`.

## Summary

Both runs use exactly the same command:

```bash
jawm "jawm_fastqc@${workflow_commit}" test \
  -p ./fastqc.yaml \
  -l ./logs
```

The first run creates the reference:

```text
logs/jawm_hashes/fastqc.hash
```

The second run validates its new output against that reference because `fastqc.yaml` contains:

```yaml
- scope: hash
  include: ./fastqc_output/my_test_file_1_fastqc/fastqc_data.txt
  overwrite: false
  reference: ./logs/jawm_hashes/fastqc.hash
```
